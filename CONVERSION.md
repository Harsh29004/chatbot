# Nexora AI — the converted stack

The platform backend is now Node.js/Express + TypeScript. The bot pipeline
stayed in Python. The frontend is Next.js with the App Router.

## What's where

| Directory | What it is | Language |
|---|---|---|
| `node-backend/` | Accounts, billing, admin, support, assistant, API keys | **TypeScript** |
| `bot-service/` | Retrieval, sheet ingest, templates, widget | **Python** |
| `next-frontend/` | The web app | **TypeScript / React** |
| `backend/`, `bot/`, `frontend/` | The originals, untouched | — |

Nothing was deleted. Both stacks can run side by side against the same MongoDB
while you compare them.

## Why the backend is split

The old `backend/` was two different jobs in one process.

One is accounts, sessions, money, credits, referrals, an admin panel and a
support inbox. That is HTTP plumbing and business rules — nothing about it
wanted Python, and it reads better in TypeScript with types on every payload.

The other is retrieval: embedding a question with `sentence-transformers`,
scoring it against stored vectors with numpy, reading whatever spreadsheet a
customer uploaded through pandas and half a dozen optional readers, and running
the LangGraph pipeline that decides between a verbatim answer, a hedged one and
a refusal. Every one of those is a Python library with no equivalent worth
migrating to — and `sentence-transformers` in particular produced **every
vector already in your database**.

So the line runs between them:

```
next-frontend (:3000)
        │
        ▼
node-backend (:8000)  ──────────►  bot-service (:8001, loopback)
        │                                   │
        └──────────────►  MongoDB  ◄────────┘
```

**Node is the only thing the internet talks to.** It authenticates the request,
meters credits, resolves *which account this is*, then calls the bot service
with a plain `user_id`. The bot service has no users, no cookies and no concept
of a credit — by the time a request reaches it, all of that is settled.

**Collections are owned, not shared.** One database, two services, no
overlapping writers:

| Written by `bot-service` | Written by `node-backend` |
|---|---|
| `bots` | `customers`, `users`, `sessions` |
| `faq_vectors`, `vector_sets` | `api_keys`, `daily_usage`, `request_log`, `credit_grants` |
| `template_overrides` | `subscriptions`, `invoices`, referral collections |
| `unmatched_queries` | `support_*`, `assistant_*`, `client_errors`, `rate_events` |

`llm_cooldowns` is the one both write, deliberately: when a model is rate
limited, both services should back off. That is why it lives in the database
rather than in a process.

## Running it

Three processes.

```bash
# 1. bot service
cd bot-service
pip install -r requirements.txt
uvicorn main:app --host 127.0.0.1 --port 8001

# 2. API
cd node-backend
npm install
npm run dev                      # :8000

# 3. web
cd next-frontend
npm install
cp .env.example .env.local       # add your Firebase values
npm run dev                      # :3000
```

Open http://localhost:3000.

Configuration comes from the existing `.env` at the repo root — **every
variable keeps the name it had**, so your current file works unchanged. The
additions are `BOT_SERVICE_URL` and `INTERNAL_API_KEY`, documented in
`node-backend/.env.example`.

## Verifying it

```bash
# backend + bot service: 66 checks, one command, boots everything
cd node-backend && npm run build && node smoke-test.mjs

# every FastAPI route is still mounted
cd node-backend && node route-parity.mjs

# frontend: 29 checks against the server-rendered HTML
cd node-backend  && node run-stack.mjs          # terminal 1
cd next-frontend && npm run build && npm start  # terminal 2
cd next-frontend && node e2e-check.mjs          # terminal 3
```

All pass clean. The backend suite covers signup and the Gmail-alias rule,
login, trial entitlement, key issue and credit metering, sheet ingest through
`/v1/ask`, gap logging, input-policy refusals, all fifteen admin endpoints,
telemetry grouping, and the billing lifecycle — every one of them now crossing
the Node/Python boundary at least once.

`route-parity.mjs` walks the live Express router stack and compares it against
the FastAPI route table: **75 of 75**, nothing dropped.

## Your data does not move

**Passwords keep working.** PBKDF2-HMAC-SHA256 is a standard construction, so
Python's `hashlib.pbkdf2_hmac` and Node's `crypto.pbkdf2` produce the same
bytes for the same inputs. The stored format is unchanged, and the iteration
count is read from each row rather than from config — so raising
`PBKDF2_ITERATIONS` does not lock out anyone who registered before the change.
The smoke test verifies a hash generated by your Python code against the Node
verifier.

**Vectors keep working.** Same model, same code, same process boundary as
before — `bot-service` *is* the original pipeline.

**Sessions, indexes and every upload format** are likewise unchanged.

A staged cutover is safe.

## The substitutions

Only the platform half was rewritten.

| Python | Node | Note |
|---|---|---|
| FastAPI | Express 4 | `Depends()` became middleware attaching to `req` |
| Pydantic | Zod | Requests only; responses are TypeScript interfaces |
| PyMongo | `mongodb` driver | Sync → async; every store function is now `async` |
| `hashlib.pbkdf2_hmac` | `crypto.pbkdf2` | Byte-identical |
| `httpx` | `fetch` | Including the SSE streaming, hand-rolled |
| `firebase-admin` (Py) | `firebase-admin` (Node) | Same product |
| Vite | Next.js 15 | App Router, server components |
| react-router | the `app/` directory | |

`llm.py` and `input_policy.py` exist in both services. That is deliberate:
each one talks to its own model providers and screens the input it is about to
act on, and they cooperate through the shared `llm_cooldowns` collection.

## Two things that changed behaviour

**One bug was fixed rather than carried over.** `assistant/context.py` read
`usage["daily_credit_limit"]`, a key that object does not have — it is
`credits_daily_limit` — so the assistant's prompt always said "of None". The
port reads the field that exists. Prompt text only.

**One real bug was introduced by server rendering, and fixed.**
`lib/markdown.ts` called `DOMPurify.addHook` at module scope, which is fine in
a browser-only build but crashes on the server, where DOMPurify has no DOM. It
now defers the hook and — with no DOM available — returns escaped plain text
rather than unsanitised HTML. Failing closed was the point: the alternative
would have shipped unsanitised model output in the server-rendered copy, before
any client code could correct it.

## What server rendering changed for users

- The landing page has prices and templates **in the HTML**, not assembled two
  round trips later. That is the page search engines read.
- Signed-out visitors to `/dashboard` get a 307 before any markup is sent. The
  old app downloaded the whole dashboard bundle first, then discovered it had
  no session.
- No auth flicker — the header knows who is signed in on the first frame.
- A wrong URL is a real 404 instead of the homepage with a 200.
- Fonts are self-hosted at build time instead of a render-blocking request to
  Google on every visit.

The admin panel stayed client-rendered on purpose: it authenticates with a key
in `sessionStorage` that dies with the tab, and server-rendering it would mean
putting that key in a cookie — where it would survive the tab closing and ride
along on every request to every route.

## If something looks wrong

The original code is still in `backend/`, `bot/` and `frontend/`. Every
converted module names its source in the header comment, and every file in
`bot-service/` except `main.py` was copied across unchanged — so any behaviour
can be compared line for line against the original it came from.
